# Web console tests

Dev-only. Nothing here is embedded in the binary or part of the Rust workspace.

    cd web-tests
    npm ci
    npm test
    npx playwright install chromium
    npm run smoke

`npm test` runs the DOM tests (node:test and jsdom) against the real modules in `crates/jaunt-web/assets`.

`npm run smoke` starts an API stub that serves the embedded assets with the daemon's CSP, then drives Chromium at 380 px, 900 px and 1440 px in the light and dark themes. It covers every screen, the node cards and list, the Connect and account menus, the navigation drawer below 900 px (focus trap, Escape, focus return) and the three-column shell at wide widths. It checks horizontal overflow, minimum font sizes, rendered text contrast, token contrast, focus rings, touch targets, dialog focus and CSP violations, and writes screenshots to `screenshots-out/after/` (git-ignored). `SCREENSHOT_DIR` changes the output directory, `JAUNT_ASSETS` serves another copy of the assets and `SMOKE_RUN_LIMIT_MS` (15 minutes) stops a run that hangs.

`npm run smoke:before` renders the same screens from an earlier commit into `screenshots-out/before/`, so the two sets can be compared side by side. It reads the assets and the smoke scripts of the commit named by `BEFORE_REF` (default `HEAD`, so run it before committing a redesign or pass the previous commit).

`npm run smoke:recording` drives the recording player in Chromium against the same stub at 380 px and 1440 px in both themes: it plays a recorded cast and a hostile one, checks layout, keyboard control, minimum font sizes, contrast, the content security policy and the requests the page makes, and writes screenshots to `screenshots-out/`. The stub serves generated casts from `smoke/casts.mjs`; a recording from a real node is not used.

`npm run smoke:terminal` drives the web terminal in Chromium at 380 px and 1440 px in both themes against a stub that speaks the `jaunt-terminal.v1` WebSocket protocol (`smoke/terminal-stub.mjs`, a hand-written server, no extra dependency). It picks a node and a login, opens a session, types `echo hello` and reads it back from the terminal buffer, resizes the window and checks the resize frame, uses the key bar, the paste event (bracketed paste) and the Copy and Paste buttons, runs a hostile output stream, floods of oversized scroll and line counts (the main thread must stay free) and a stream of terminal queries (only the allowed replies may reach the node), checks that the picker comes back from the breadcrumb, Choose another node and the rail after a session ended, runs the picker and a session with 40-, 50- and very long node names and labels (no horizontal scroll), checks the close, revoked and denied states, that nothing reconnects by itself and that leaving the page closes the socket, then asserts layout, font sizes, contrast, touch targets, CSP and requests. Screenshots go to `screenshots-out/terminal-*.png`.

`npm run smoke:c0` inserts every C0 control byte into `x ESC [ 4 9 9 9 <final>` for the finals L S T M Z @ P X b (every position for L, positions 1, 2, 4 and 6 for the others to keep the run short; 50 repetitions each), once through the raw terminal and once through the guarded writer, and fails if any combination keeps the main thread busy for 100 ms. Each case runs on its own with a deadline (`C0_CASE_LIMIT_MS`, 10 s): a case that does not answer is stopped through the DevTools protocol, marked with `!` and counted as a failure, so a hang cannot stall the run. Set `JAUNT_ASSETS` to a copy of the assets with a protection removed to print the matrix of what that protection stops instead of failing.

`npm run smoke:marks` is an oracle for the combining-mark limit in Chromium with the real canvas renderer. The limit itself lives in `js/terminal/cells.js`: it sits where xterm adds a code point to a cell (the only place a cell grows, reached only from xterm's own print path), so xterm's parser decides what is text and what joins, and the page keeps no parser or width table of its own. The budget at that moment is taken for the largest font the surface can show (24 px in the live terminal, the fixed 14 px of the player) at the current device scale, and every row xterm paints is cut again to the budget of the device cell it is painted at, which covers a later zoom or a move to a screen with a higher scale. The oracle runs four lanes in parallel (the live terminal and the player, each at device scale 1 with a 14 px font and at device scale 4 with a 24 px font), each with the fixed reproducers (strings cut by a non-ASCII letter, separators that xterm does not treat as a reset, a wide character dropped at the right margin, a resize between a base and its marks, 63 marks in three frames, 300 ideographic tone marks, supplementary variation selectors) and 1300 seeded random cases built from escape introducers, 8-bit controls, terminators, C0 controls, DEL, lone and paired surrogates, swallowed letters, malformed and ordinary CSI, mode switches and runs of zero-width characters from every range, written in pieces split at random byte offsets (live, through the streaming decoder) or code unit offsets (player). Before every case it resets both terminals with `ESC c` through `writeSync`. After the case has been drawn it checks that no cell holds more than seven code points or more UTF-16 units than the measured device cell width allows (`floor(506 / width)`, the 512-pixel texture page), and compares every cell, its width and attributes, the cursor and both buffers with an unpatched xterm loaded in a separate frame and fed through the same guard: a cell must equal the raw cell with the excess marks removed. A growth phase then writes the shortest hanging forms (a letter or a wide base with six supplementary variation selectors, a letter with six marks, a letter with 63 marks) on the first and the last row at 14 px with device scale 3 and 4, raises the font to the largest size the surface allows, then doubles the device scale, and checks after each step that the page still answers and that no cell holds more than the new device cell allows. A case or a growth step that does not finish drawing within 5 s is stopped through the DevTools protocol and fails, a fixed case must finish within 500 ms, and the whole run is stopped after 6 minutes. `MARKS_SEED` and `MARKS_CASES` (total random cases, default 5200) change the run; a failure prints the seed, the case index and the code points.

Known limits of the output protection, kept here so nobody has to rediscover them:

- Whole-screen operations (reset with `ESC c`, `ESC # 8`, alternate-screen switches, `ESC [ 2 J`, scroll at the clamp) cost time proportional to rows times columns. A node that streams them without pause can keep the tab busy for as long as it streams, spread over many chunks; the page stays responsive and Disconnect keeps working. This is the same as any heavy output.
- A laptop that sleeps with a dead socket is reported as lost 40 to 60 seconds after it wakes, because the silence check waits for two on-time checks after the tab is visible again.
- The vendored canvas renderer can raise an occasional `TypeError` about a cell after a reset (seen once in 200 runs of an isolated loop; the terminal kept drawing). The combined-character limit works around a loop in the same vendored file and is tied to its 512-pixel texture page (`ATLAS_BUDGET` in `js/terminal/cells.js`). Both belong to the next vendor upgrade, which is a separate slice.
- The limit reaches into private parts of the vendored xterm (`_core._inputHandler.print`, the line methods behind it, `_core._renderService._renderRows` with its scheduler and the renderer's device cell size). If they are not found, the terminal and the player refuse to start and say that they cannot start safely; `unit/terminal-cells.test.mjs` fails on a library that moved them.
- The cell budget, measured in Chromium with the default monospace font (code units of one cell; a base with its six marks never needs more than 14):

  | device scale | live terminal (14 to 24 px) | player (14 px) | device cell at 24 px |
  |---|---|---|---|
  | 1 | 32 | 54 | 14 px |
  | 2 | 16 | 28 | 28 px |
  | 3 | 10 to 11 | 18 | 43 px |
  | 4 | 8 | 14 | 57 px |

  Where the budget is below 14, long sequences of supplementary characters on one base are shortened: a subdivision flag (a black flag with five tag characters and a cancel tag, 14 units) keeps only its first tags in the live terminal from device scale 3 on, and in the player above device scale 4 or after a zoom. Ordinary text in every script, emoji with skin tones or joiners, keycaps and single variation selectors fit at every scale in the table.
- The cut at paint time changes the stored text and is not undone: once a row has been drawn at a higher device scale, marks above that scale's budget are gone from it, also from copied text (select all and copy returns the shorter text), and going back to the earlier zoom does not bring them back. Rows that are never drawn at the higher scale keep their marks.
- A full repaint at a very high device scale (9 to 15, for example a large zoom on a dense screen) is slow once, in the order of 250 to 600 ms, then drawing returns to normal speed.
- The cut at paint time relies on every drawing of terminal text going through xterm's render service (`_renderService._renderRows`, scheduled by its own frame callback) and on the browser reporting a new device scale before it runs animation frames, which Chromium does. A cell already stored with more units than a new budget allows would freeze the tab if it were drawn at the higher scale through any other path or before that report; none was found in the vendored 5.5.0 with the cursor not blinking. Glyphs without marks stay unprotected at device cells of 254 px and more, where every cell is drawn on a full 512-pixel scratch canvas; probes of very wide glyphs at device scale up to 18 found no hang.

`npm run smoke:csi` feeds the real terminal adapter every CSI sequence from final byte `@` to `~`, with and without the `?`, `>`, `<`, `=` markers and each intermediate byte, with first parameters of 999999999 and 2147483647, one sequence at a time after a printable character, and fails if any of them keeps the main thread busy for 500 ms or more. It takes a few minutes. `CSI_SWEEP_FINALS=Lb` narrows it to some final bytes, `CSI_SWEEP_GUARD_MS` changes the hang guard for each group and `CSI_SWEEP_RUN_LIMIT_MS` (20 minutes) stops the whole run and its browser.
